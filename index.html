A self-checking AI swarm: the ledger

Project VAMPIRE SAVED is a fan modification of the 1997 arcade game Vampire Savior (Capcom CPS-2): it adds the three characters the game's sibling releases carry, on the original engine, under one rule — every match that does not involve them must stay bit-for-bit identical to the unmodified game. The engineering is done by AI agents (Claude, in Claude Code sessions): one orchestrator per working session, which spawns workers to measure and read, with a human maintainer who rules on anything a player could feel.

The agents check their own work. Before an action — a build of the game, a freeze of a release, a change to a test's expected results, a recommendation to the maintainer such as closing a ticket, a session's push — the orchestrator writes the claim it is about to act on and the evidence it rests on, and an adversarial rule-checker must find nothing wrong with it. This page measures how often the agents get that right the first time, what the checker catches, and whether the checker itself is alive.

How a check works

  1. The packet. The orchestrator states one claim — what it concludes, what it rests on, and what it did not test — and lists the files that are its evidence. No narrative: a checker handed a summary inherits its framing.
  2. Two readers, one plant. Two fresh agents with no other context each get one packet. One packet is the real one; the other is a plant: a known-bad packet drawn from a calibrated set, built from a real past mistake. Which reader gets which is drawn at random, and neither knows.
  3. Five questions. Each reader answers the same five questions (below) from the files alone, each OK, VIOLATED or N-A with its evidence, and a verdict.
  4. The plant must be caught. If the planted packet does not come back VIOLATED on its expected question, the run is VOID: a reader that passes a known-bad packet proves nothing about the real one.
  5. A VIOLATED verdict stops the action. The orchestrator answers each violated question in writing (the resolution, recorded verbatim), fixes the work or the claim, and prepares a new packet: a re-check. The action proceeds only on an OK.

Terms

Session
One sitting of the orchestrator with the maintainer, named 14z-N (a fixed prefix, then a counter).
Action
One thing put to the rule-checker and every re-check of it until one passes or the action is dropped. Its kind is its decision: build, freeze, expectation, recommendation, procedure.
Run
One rule-checker check of one packet: two readers, one real packet, one plant.
First run
An action's first run that licensed anything (a VOID run never counts as one).
Re-check
Any run of an action after its first; each follows a written resolution of what was violated.
Plant / CAUGHT / DEAD
The known-bad packet beside the real one. CAUGHT: the reader found its violation. DEAD: it did not, and the run is VOID.
VOID
A run whose plant was not caught: it licenses nothing, and it is not counted in the rates.
Resolution
The orchestrator's written answer to each violated question, recorded with the run.
Calibration
A run that checks the checker itself on a fixture of known verdict; not an action.
Not run
A packet prepared but never sent to readers (its writer caught a fault first); not counted.
Decision kinds
build: a romset built for testing; freeze: a release of the romsets and their expected results; expectation: a test's frozen expected result changed; recommendation: a report or recommendation to the maintainer (closing a ticket among them); procedure: a session's working method, read from its transcript before a push or a close.
MEASURED / DERIVED / ESTIMATED
Every figure's class. MEASURED: read from a record the work wrote. DERIVED: arithmetic on measured figures, the formula stated. ESTIMATED: a heuristic, its rule stated, and it can be wrong.
Resolved
An action whose last run is VIOLATED, answered question by question with `rulecheck resolve` (what changed, or why the finding is accepted) and not run again. A VIOLATED verdict stops the action until it is resolved; the rule has never required a re-check that comes back OK.
Eras
Three spans of sessions, by how actions ended. To 14z-182 a VIOLATED run was resolved and the action went on, almost never re-checked. From 14z-183 a re-check until OK became common; no rule change is recorded there, the boundary is read from the per-session counts (14z-183 is the first session where most actions end OK). From the first session whose runs record their action (14z-212), runs are grouped into actions exactly; before it the grouping is ESTIMATED (see Linking).
Linking
The ledger before 2026-10-29 records no action id, so its runs are grouped into actions by rule: a subject that names the run it follows ('after run 682'), else similar wording within the session (ESTIMATED). Since then every run records its action.
