> **STATUS (14z-174, 2026-09-21): SHIPPED. Every slice A1-A6 is landed and gated.**
> The release carries `apply_release.html` in each platform directory — one
> self-contained file a player double-clicks — generated by
> `tools/gen_applier_page.py` from that release's own manifest and patches, and held
> by `tests/test_applier_page.sh` (it equals `apply_release.py` member for member on
> both variants, refuses what it refuses, and carries no network primitive) and

## 2. THE RECOMMENDATION: ONE STATIC HTML PAGE, RUNNING ENTIRELY IN THE BROWSER

Not a per-OS executable. The reasoning is not aesthetic:

- **It dodges the problem we are already stuck on.** #144 and #145 exist because an
  unsigned binary is hard to get an OS to run. Shipping a *second* unsigned binary —
  one that asks for the player's ROM files — doubles that problem and asks for more
  trust, not less. A web page needs no signature, no notarisation, no SmartScreen
  exception and no install.
- **It is genuinely OS-agnostic**, which is what the maintainer asked for first.
- **It needs no toolchain from us and no Python from them**, which is the whole
  complaint.

**THE HARD CONSTRAINT, and it is a rule-7 matter: the page must be provably
client-side.** No upload, no telemetry, no network call after load. **Since 14z-174 that
is enforced by the BROWSER, not by our grep:** the page carries a Content-Security-Policy
of `default-src 'none'; connect-src 'none'; form-action 'none'; base-uri 'none'`, so the
engine refuses every network primitive — including the ones nobody thought to enumerate —
and `tools/gen_applier_page.py` refuses to emit a page whose policy is missing or
weakened. A denylist of known primitives is kept beside it as an independent
authoring-time check, because a CSP violation surfaces at run time in a console where a
scan surfaces at generation time; but the denylist is NOT the guarantee, and it is not
treated as one. That correction came from a rule-checker, which observed that the scan
was an enumeration with a single control and named five primitives it could not see —
one of which the page itself used. The player's ROMs
are commercial dumps; a page that posted them anywhere would be a copyright problem
and a betrayal of the reason this project ships deltas instead of bytes. It must also
carry the same per-member SHA-1 verification `apply_release.py` does, or it is a worse
applier wearing a nicer coat.

## 2a. THE ONE CORRECTION TO §2 (measured 14z-174)

§2 assumed the page could sit beside `manifest.json` and `patches/` and read them.
**It cannot.** From `file://` a page is refused `fetch`, `XMLHttpRequest` and
cross-file `import` alike, in Chrome and Firefox both (the table is in
`docs/platform/gotchas.md`). The page is therefore ONE file with this release's
manifest and its 20 patches (base64) and the three applier modules inlined — 3.4 MB,
generated by `tools/gen_applier_page.py`.

That is strictly better for the ruling it implements: shipping in the asset was meant
to make version-matching impossible for the player to get wrong, and a page that
physically contains its release's patches cannot be pointed at another release at
all. It also makes the hard constraint of §2 checkable by reading the file: there is
no code in it that could send anything anywhere, and the generator refuses to emit a
page that has any.

## 3. FEASIBILITY — MEASURED, NOT ASSUMED

Every capability the page needs exists natively, so the dependency count is **zero**:

| need | mechanism | evidence |
|---|---|---|
| read the player's dumps | `<input type="file" multiple>` -> `ArrayBuffer` | standard |
| read zip members (DEFLATE) | `DecompressionStream("deflate-raw")` | round-tripped 200,000 bytes byte-identical |
| write `vsavjw.zip` (DEFLATE) | `CompressionStream("deflate-raw")` | same test |
| SHA-1 every member | `crypto.subtle.digest("SHA-1", …)` | agrees with Python's digest on the same input |
| decode the 20 patches | **a JS port of `vcdiff_decode`** | **20 of 20 patches decoded to the manifest's exact SHA-1, 0.2 s** |
| hand over the result | `Blob` + download link | standard |

**The port is the only real work, and it is done and proven** (the measurement above,
against the shipped `release/merged-m19` patches). Everything else is wiring.

**WHICH OF THOSE ROWS IS GATED — ALL OF THEM, SINCE 14z-174.** The decoder by
`tests/test_applier_vcdiff.sh` (every shipped patch, every static tier). The zip
reader, the SHA-1s and the whole pipeline by `tests/test_applier_page.sh`, which
runs these modules over `$ROMDIR` and requires the result to equal
`apply_release.py`'s member for member. And the three rows that were measured under
node rather than in a browser — `deflate-raw` both ways, `crypto.subtle` SHA-1, the
file pickers — by `tests/test_applier_page_browser.sh`, which drives the shipped
page from `file://` in Chrome and reads the set key it prints.

**WHAT A BROWSER RUN DOES NOT COVER, stated rather than glossed:** only Chromium is
driven by a gate. Firefox was measured by hand on the capability probe (secure
context, SHA-1, `deflate-raw` round trip, and the three blocked read routes — all
as Chrome) but is not gated. **WebKit/Safari is UNMEASURED**, and it is the default
for a double-clicked `.html` on macOS, so it matters most of all; `qlmanage`'s
WebKit does not run the page. The page's own first section names any missing
capability instead of failing obscurely, which is the mitigation, not a substitute.

The shape of the job, from the M19 manifest: a **97.0 MB** source blob rebuilt from 51
members of 3 zips; **20** patches totalling 2.62 MB of VCDIFF; 12 pristine copies; **32**
output members, 73.7 MB uncompressed; **83** SHA-1 verifications; largest member 4.2 MB.
Naive peak memory is ~171 MB, which a browser tab holds, but see the slices.

## 4. SLICES — ALL LANDED (A1 at 14z-173, A2-A6 at 14z-174)

- **A1 — the decoder, extracted and locked.** `tools/applier/vcdiff.mjs` +
  `tests/test_applier_vcdiff.sh`: every shipped patch decoded to the manifest's exact
  SHA-1.
- **A2 — the page, offline.** `tools/applier/page_shell.html` (the UI),
  `tools/applier/zip.mjs` (a reader for the player's dumps, a writer for the romset)
  and `tools/applier/applier.mjs` (the logic, step for step the Python tool's),
  inlined into one file by `tools/gen_applier_page.py`. Peak memory in a tab is about
  300 MB, which the page says up front.
- **A3 — the refusals.** Every static fragment of every message `apply_release.py`
  can print must exist in the page's applier — read out of the Python file's SYNTAX
  TREE by `tests/test_applier_page.sh` §4, so a new refusal there fails the gate until
  the page has one. Four are exercised end to end on both tools: a modified dump, a
  truncated dump, a corrupted patch, a tampered manifest. **Two refusals did not
  exist in either tool until this gate asked for them** — a damaged or half-copied
  dump raised a raw parser error at the player in both; both now name the file.
- **A4 — the optional QSound BIOS member.** A two-way choice in the page with the
  README's own guidance, and the gate requires that choosing "leave it out" stops the
  page ASKING for `qsound_hle.zip`, not merely dropping the member.
- **A5 — THE FIDELITY CONTRACT.** Member for member, order, every zip header field,
  and the manifest's `applied_set_key` for BOTH variants — and the SHIPPED file is what
  is measured: every platform dir's `apply_release.html` must equal a fresh generation,
  and the browser gate loads the shipped file itself. (Until a rule-checker asked, both
  gates measured a fresh generation and "the shipped page is that generation" was assumed
  by everything.) What node cannot reach is the page's own WIRING — `page_shell.html`'s
  calls into the modules — which the browser gate covers by driving the real controls and
  checking the set key the page prints. **The container bytes are
  deliberately not compared**, because `CompressionStream` is not byte-comparable to
  `zlib.compressobj` and the engines differ from each other
  (`docs/platform/gotchas.md`); what no encoder can change is the member bytes, which
  is what every emulator, every fingerprint and the set key read.
- **A6 — where it lives.** `release/<name>/{fbneo,mame,mister}/apply_release.html`,
  generated by `tools/package_release.py` and re-generated per platform by
  `tools/package_release_platforms.py`. It is in the ruled release inventory
  (`test_release_roundtrip.sh` §4) and in every published asset's self-sufficiency
  definition (`test_release_asset_shape.sh`, `tools/upload_release_assets.sh`).

## 5. NOT IN SCOPE

- Replacing `apply_release.py`. It stays the tool of record, the thing the gates run,
  and the route for anyone who prefers a command line. The page is an alternative
  front end to the same manifest, never a second definition of the romset.
- Building or shipping the emulators. That is #144/#145.
- Anything that makes the page a prerequisite: a release must remain usable with
  Python alone.

## 6. RULED — and the one question that was mine to answer

All three were put to the maintainer on 2026-09-20 and answered the same day.

1. **Where does it live? — RULED: a local file in the asset.** *"preferably a local
   file in the asset"*. So the page ships inside each release package beside
   `apply_release.py`, is opened from disk, and there is no hosted surface to
   maintain or to prove is not uploading anything.
2. **Per release, or one generic page? — I asked this badly and the maintainer said
   so** (*"not sure what you mean"*). Restated: the page could either carry this
   release's difference files inside it, so it only ever builds this version; or be a
   general reader that you point at any release's `manifest.json`, so one copy of the
   page works for every future version. **It follows from (1) and does not need
   asking again:** shipping inside the asset means the page sits next to that
   release's own `patches/` and `manifest.json`, so it reads the files beside it and
   is automatically correct for the release it shipped with. One page per release, no
   version-matching for the player to get wrong.
3. **Is a browser page acceptable for players handing it ROM files? — RULED: yes**,
   *"in any case that's not a blocker as of now so we can assume yes"*. The
   client-side constraint in §2 stands regardless, and the README will say plainly
   that nothing leaves the machine.

**That open item is CLOSED (14z-174):** `deflate-raw` and `crypto.subtle` were
confirmed in Chrome and Firefox from `file://`, and Chrome's run is now a gate.
Which browsers are in scope is answered by measurement where it could be —
Chromium gated, Gecko measured by hand, **WebKit unmeasured** — and by the page
itself, which names any capability it cannot find rather than failing obscurely
(§3).
